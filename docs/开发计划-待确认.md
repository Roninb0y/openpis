## 一、项目理解总结

### 1.1 项目目标

- **OpenPIS-Lite**：面向大学生/求职场景的简版数字标牌（乘客信息系统 PIS）开源项目，由 141 页的《PIS媒体发布软件用户使用手册 v2.0》精简而来。
- 6~10 周做出一个**可运行、可演示、可写进简历**的最小可用系统（MVP）。
- 核心理念"**先闭环，后精致**"：优先跑通主线业务闭环——
  **上传媒体 → 组成播表 → 设计布局 → 布局+播表绑成栏目 → 栏目排成计划 → Web 播放端按时自动播放 → 播放数据回流报表**。
- 代码结构清晰、文档完整、Docker 一键启动，方便后续逐步迭代。

|---|---|

| 工具链 | Git、IDEA/VSCode、Apifox（接口测试）、DBeaver（数据库）、Docker（后期容器化） |

规划文档中提到、但 Day2~Day5 实施文档**尚未使用**的：MyBatis-Plus、Redis、WebSocket/STOMP、MinIO、ECharts、SpringDoc/Swagger、Maven 多模块、Spring Scheduler。→ 见第二部分待确认项。

业务链：**媒体 → 播表 → 布局 → 栏目 → 计划 → 播放 → 日志报表**

## 三、开发阶段拆解

> 阶段 0~4 有代码级文档跟随，主要是照做+修 bug；阶段 5~8 无文档，需要先设计再实现；每阶段结束提交一次 Git。

### 阶段 0：项目骨架（约 0.5 天，起步指南已有完整步骤）

- **目标**：前后端能跑、能通、进了 Git。
- **任务**：
  1. 环境检查（JDK 17 / Node 18+ / MySQL 8.0 / Git / Docker）
  2. 创建后端 `openpis-server`（Spring Boot 3.2 + Web + JPA + MySQL Driver + Lombok + DevTools），配置 `application.yml` 与 CORS
  3. 创建前端 `openpis-web`（Vite vue-ts 模板 + Element Plus / Pinia / Router / Axios）
  4. 建库 `openpis`（utf8mb4），写 `/api/hello` 测试接口
  5. `.gitignore` + 初始提交
- **交付物**：可启动的前后端骨架仓库。
- **验证**：浏览器 `localhost:5173` 点击按钮能取到后端 8080 的返回；`git log` 有初始提交。

### 阶段 1：登录认证（Day2，约 1 天）

- **目标**：JWT 登录/登出/路由守卫闭环，搭好后台框架。
- **任务**：
  1. `sys_user` 表 + User 实体/Repository
  2. JwtUtil、JwtAuthenticationFilter、SecurityConfig（无状态、BCrypt、`/api/auth/**` 放行）
  3. Result 统一返回体、LoginRequest/LoginResponse、AuthService、AuthController
  4. DataInitializer 初始化默认 admin（BCrypt 加密）
  5. 前端：axios 封装（token 拦截、401 跳转）、auth API、Pinia user store、登录页、Dashboard 框架（侧边栏+顶栏+`<router-view>`）、路由守卫
- **交付物**：认证体系 + 后台布局框架（后续所有模块挂在其子路由下）。
- **验证**：Apifox 测登录（正确 200 / 错误 401）；未登录访问 /dashboard 被拦截到登录页；登录后显示欢迎信息与角色；退出回登录页；手动清 token 后接口 401 并自动跳登录。

### 阶段 2：媒体管理（Day3，约 1 天）

- **目标**：素材进系统并可管理。
- **任务**：
  1. `material` 表 + 实体/Repository
  2. 上传目录/大小配置（`file.upload.path`，multipart 上限 500MB）+ `/uploads/**` 静态映射
  3. MaterialService：类型判定（image/video/text）、大小校验、UUID 重命名按类型分目录、图片缩略图（thumbnailator）
  4. MaterialController：upload / list（分页+类型+关键词） / detail / delete（文件+缩略图+记录同步删）
  5. SecurityConfig 放行 OPTIONS
  6. 前端：material API（含 PageResult 类型）、列表页、UploadDialog、PreviewDialog（图片/视频/文本）、侧边栏菜单
- **交付物**：完整的媒体管理模块。
- **验证**：分别上传 jpg/png/mp4/txt 成功且文件落盘 `uploads/materials/{type}/`；浏览器直接访问文件 URL 可打开；分页/类型筛选/搜索正常；预览正常；删除后文件与记录同步消失；超限文件被拒。

### 阶段 3：播表管理（Day4，约 1 天）

- **目标**：把素材组织成有序播放列表。
- **任务**：
  1. `playlist` / `playlist_item` 表 + 实体/Repository/嵌套 DTO
  2. PlaylistService：创建、详情（批量查媒体防 N+1）、更新（全量替换）、删除（级联删 items）
  3. PlaylistController CRUD
  4. 前端：playlist API、列表页（类型/名称搜索）、PlaylistForm 两栏页（素材池类型过滤+多选添加、VueDraggable 拖拽排序、逐项时长、清空）、路由 + 菜单
- **交付物**：播表管理模块。
- **验证**：建 3 项播表 → 拖拽换序 → 保存 → 编辑回显顺序正确 → 删除播表后查 DB 确认 items 级联清理；素材池按播表类型过滤逻辑正确。

### 阶段 4：布局管理（Day5，约 1~1.5 天，项目最大亮点）

- **目标**：Konva 可视化布局编辑器。
- **任务**：
  1. `layout` 表（modules JSON）+ 实体/Repository/DTO
  2. LayoutService（Jackson 序列化/反序列化）+ Controller CRUD
  3. 前端：konva + vue-konva 注册；LayoutEditor——5 种分辨率预设、画布等比缩放（最大 800px 宽，坐标×scale 显示、÷scale 存原值）、模块拖拽、Transformer 缩放（最小 50×50、transformend 重置 scale）、右键菜单设类型（四色）、参数表精确调 x/y/w/h、层级置顶/上移/下移/置底、编辑态回显（moduleCounter 防止 ID 冲突）
  4. 路由 + 菜单
- **交付物**：布局编辑器 + 布局列表管理。
- **验证**：按 Day5 第十四步 13 条手工清单全部通过；保存后重新打开布局，坐标/类型/层级与保存时一致；用 Apifox 确认后端存的是**原始分辨率坐标**（非缩放后坐标）。

### 阶段 5：栏目管理（无文档，约 1~2 天，动手前先出设计稿）

- **目标**：布局 + 播表结合成可排期的"栏目"。
- **任务**：
  1. **先确认 `module_playlists` JSON 结构**（如 `[{moduleId, playlistId}]`）与校验规则：模块媒体类型与播表类型匹配、允许留空的模块策略、布局变更后的绑定失效处理
  2. `program` 表 + Service（校验布局/播表存在、模块全覆盖可选校验）+ Controller CRUD
  3. 前端：选布局 → 按布局模块生成绑定列表（每个模块下拉选对应类型播表）→ 播放类型选择（loop 垫播 / insert 插播 / emergency 紧急）→ 复用 Konva 只读渲染做布局缩略图预览
- **交付物**：栏目管理模块 + JSON 结构设计说明。
- **验证**：创建栏目绑定 3 个模块的播表；类型不匹配被前端拦截/后端校验拒绝；删除被引用的布局/播表时有提示或级联策略生效；详情回显正确。

### 阶段 6：计划管理（无文档，约 1.5~2 天，动手前先出设计稿）

- **目标**：栏目按日/周排期，支持发布/撤销，并实现"当前应播计划"调度算法。
- **任务**：
  1. **先确认 `schedule` JSON 结构**（日计划：时间段数组；周计划：星期+时间段）与时间冲突规则（同段多计划按 play_type 优先级 emergency > insert > loop）
  2. `plan` 表 + 计划-栏目关联（JSON 内嵌或明细表，设计稿定）
  3. 发布/撤销状态机（草稿 → 已发布 → 下线/撤销）
  4. "当前应播计划"解析算法 + `GET /api/player/current` 接口（播放端取数用）
  5. 前端：日/周切换的时间轴编辑、选栏目+时间段、发布/撤销操作、计划列表
- **交付物**：计划管理模块 + 调度解析算法（面试重点素材）。
- **验证**：建日计划（09:00–12:00 栏目A）和周计划（周一 08:00–10:00 栏目B）→ 发布后模拟不同当前时间调 `/api/player/current`，返回结果正确 → 构造时间重叠验证优先级 → 撤销后返回空/默认计划。

### 阶段 7：Web 播放端（无文档，约 1.5~2 天，业务闭环的关键一步）

- **目标**：全屏网页播放器按计划自动播放。
- **任务**：
  1. `/player` 独立全屏路由（URL 带设备码、免登录，与管理后台隔离）
  2. 取数：进入时拉 `/api/player/current` + 建立 WebSocket（Spring WebSocket）接收计划变更推送；降级方案 30s 轮询
  3. 播放引擎：按布局渲染模块——video 模块循环播视频播表、image 模块轮播图片、text 模块滚动/翻页字幕；栏目/计划切换平滑过渡（不闪黑屏）
  4. 分辨率自适应：布局坐标等比缩放到浏览器窗口
  5. （可选）device 心跳更新
- **交付物**：可演示的播放端页面。
- **验证**：打开 `/player?code=xxx` 按当前计划播放，画面与布局比例一致；后台改计划/发布新计划后 ≤30s 播放端自动切换；多个模块同时各播各的播表；窗口缩放布局等比适配；断网恢复后能重新拉取计划。

### 阶段 8：播放日志与报表（无文档，约 1 天）

- **目标**：数据回流，闭环最后一环。
- **任务**：
  1. `play_log` 表 + 上报接口（素材开始/结束，播放端批量上报防丢）
  2. 统计接口：按日播放次数、按栏目/素材聚合
  3. 前端 ECharts 报表页（柱状/折线，可并入 Dashboard 首页）
- **交付物**：播放报表页。
- **验证**：播放端运行 10 分钟产生合理日志量；报表数字与 `play_log` 原始数据 SQL 抽查一致。

### 阶段 9：容器化、修整与包装（约 1~2 天，对应规划"阶段二"）

- **目标**：一键部署、可对外展示。
- **任务**：
  1. Dockerfile（后端、前端）+ docker-compose.yml（mysql + server + web/nginx）
  2. 配置环境变量化（DB 密码、JWT secret、上传目录）
  3. 修复 1.4 节列出的已知 bug
  4. seed 演示数据（可选）、README（背景/架构图/截图/部署方式）、演示视频
  5. 可选：GitHub Actions CI
- **交付物**：可发布的 GitHub 仓库。
- **验证**：干净环境下 `docker compose up -d` 后，从登录 → 上传 → 播表 → 布局 → 栏目 → 计划 → 播放全流程可走通。
